[サンドーム福井 コンサート・ライブ情報](https://sundome.take20m.dev/)というサイトを運営しています。
公演の予定と、チケットの先行・抽選の受付期間を毎晩自動で集めて掲載しています。

情報を集めているのは、スクレイパーではなく Claude Code のヘッドレスモードです。
GitHub Actions の cron から毎日 `claude -p` を叩き、日本語で書いた指示書を渡して WebSearch と WebFetch で調べさせています。

作ってみて一番手こずったのは、LLM が間違ったことを言うことではありませんでした。
毎回ちょっとずつ違うことを言うことでした。この記事はその記録です。

### 仕組み

まず全体像です。

```
GitHub Actions (毎日 JST 17:00)
  └─ claude -p collector/prompt.md   ← 調査手順を日本語で書いたファイル
       WebSearch / WebFetch で調べて events.json を書く
  └─ validate.mjs → POST /api/ingest
  └─ Cloudflare Workers + D1 → 一覧・詳細ページ / RSS
```

収集ロジックはコードではなく Markdown です。
「会場公式カレンダーを検索しろ」「見つけた公演ごとにチケット受付を逆引きしろ」「特設ページを見つけたら本文を読め」と手順を日本語で書いてあるだけで、
実際に何をどの順で検索するかは Claude Code が決めています。for 文もリトライも書いていません。

DB への書き込み経路は `POST /api/ingest` の 1 本だけにしてあります。これが後で効いてきます。

### 同じ公演が 2 件に増える

最初に起きたのは、同じ公演が DB に 2 件並ぶ現象でした。

```
FANTASTICS
FANTASTICS from EXILE TRIBE
```

どちらも情報源に実在する表記です。LLM は嘘をついていません。
ある晩は公式サイトの短い方を、別の晩はニュース記事の正式名称を拾ってきただけです。

問題は、こちら側がアーティスト名を識別子の一部に使っていたことでした。名前が変われば ID が変わり、別の公演として増えてしまいます。

対策は、識別子から名前を追い出すことでした。

```ts
const eventId = `ev-${ev.date}`;
```

サンドーム福井はホールが 1 つしかないので、1 日に 2 公演が並ぶことがありません。つまり日付が公演を一意に決めます。
`ev-2026-10-11` という ID にしてしまえば、名前がどう揺れても書き込み先は同じ 1 行です。

ドメインの制約をキー設計に持ち込んだ形なので、多目的ホールが複数ある会場ではこの手は使えません。
ただ **LLM に ID を作らせない** という原則自体は、どこでも通用すると思います。

チケットの受付（FC 先行、一般発売など）は 1 公演に複数ぶら下がるので、日付だけでは足りません。
ここは名前を使わざるを得ないので、正規化してからハッシュを取っています。

```ts
function normalizeKey(s: string): string {
  return s.normalize("NFKC").toLowerCase().replace(/\s+/g, "");
}
```

NFKC で全角・半角を統一し、小文字化し、空白を全部消してからハッシュ化します。実際に計算するとこうなります。

```
"FC先行(抽選)"     → "fc先行(抽選)"  c769a638
"ＦＣ先行（抽選）"  → "fc先行(抽選)"  c769a638
"fc 先行(抽選)"    → "fc先行(抽選)"  c769a638
```

3 通りの表記が同じ ID に着地します。

さらに、情報源が受付名そのものを書き換えるケースもありました。
`NF member 一次抽選` が `全ステイタス対象1次抽選受付` に変わる、というものです。
これは正規化では吸収できないので、受付期間が完全に一致する既存行があれば、同じ申込とみなして ID を引き継ぐようにしています。
名前が変わっても期間まで同時に変わることは稀なので、期間を指紋のように使う発想です。

### 昨日あった期間が、今日は消える

次に起きたのは、もっと厄介でした。昨日まで表示されていた受付期間が消えるのです。

```
1 晩目  LLM「一次抽選 4/24 12:00 〜 5/6 23:59」  → DB に入る
2 晩目  LLM「一次抽選」（期間は null）           → 上書きされて消える
3 晩目  LLM「一次抽選 4/24 12:00 〜 5/6 23:59」  → 復活
```

LLM が嘘をついたわけではなく、その晩はページを読み切れなかっただけです。
でも素直に UPDATE すると、せっかく取れていた情報を自分で消してしまいます。

ポイントは `null` の意味でした。`null` は「受付期間が無くなった」ではなく「今夜は分からなかった」です。
だから `null` では上書きしないようにしました。

```ts
starts_at: l.starts_at ?? old?.starts_at ?? null,
```

この考え方を他の項目にも広げていくと、ひとつの原則にまとまりました。状態は良くなる方向にしか動かさない、というものです。

| 対象 | 許す | 禁じる |
| --- | --- | --- |
| 期間・URL | `null` → 値あり | 値あり → `null` |
| 情報の確度 | 推定 → 公式 | 公式 → 推定 |
| 売り切れ | 販売中 → 売り切れ | 売り切れ → 販売中 |
| 行の存在 | 出現したら追加 | 1 回消えただけでは削除しない |

ラチェット（爪車）と同じで、締める方向には回りますが、緩む方向には回りません。

これが効くのは、LLM の出力が毎晩ランダムに揺れるからです。
両方向に動ける DB は揺れをそのままなぞってランダムウォークし、良い夜の成果が悪い夜に打ち消されるので、いくら収集を繰り返しても状態が良くなりません。
向きを付けると、良い夜の成果だけが積み上がり、悪い夜は「何も起きない」で終わります。

もちろん代償はあります。売り切れが解除されて再販されても追従できませんし、情報源が誤りを訂正しても確度は下がりません。
このサイトでは「情報が古いまま残る」害より「正しい情報が消える」害の方が大きいと判断できたので許容していますが、
在庫がリアルタイムに動くシステムなら、この設計は選べないと思います。

### 1 回の取りこぼしが「新規発見」として通知される

更新は RSS で配信していて、Slack で購読しています。
ここで気づいたのが、毎晩 30〜95 件も通知が飛んでいることでした。

{/* TODO(体験): 大量の通知に気づいたときの様子。何を見て気づいたか、そのとき何を思ったか。1〜2 行 */}

原因のひとつは、収集結果が毎晩少しだけ揺れることでした。
20 件取れる夜と 19 件の夜があり、収集に現れなかった行をその場で削除すると、
翌晩また見つかって「新規発見」として通知が飛びます。同じ情報が何度も届くわけです。

そこで削除にもラチェットを入れました。1 回消えても削除せず、2 回連続で消えたときだけ削除します。

```ts
if (row.missed_count >= 1) {
  // 2 回連続で現れなかったので削除
} else {
  // missed_count を +1 して様子を見る
}
```

さらに、行を削除しても内容のハッシュだけは残すようにしました。
これがないと、削除された行が後日復活したときに「前回の記録がない」から「新規追加」と判定されてしまいます。

### 通知するかどうかは、別の問題だった

削除の件が片付いても、まだ通知は多いままでした。
ここで気づいたのは、データを正しく保つことと、それを人に知らせるかは別問題だということです。

差分の検知には内容のハッシュを使っています。重要なのはハッシュに何を入れるかでした。

```ts
const hash = sha256(JSON.stringify([starts_at, ends_at, confidence, sold_out]));
```

材料は 4 つだけで、名前も URL も入れていません。
受付名が `NF member 一次抽選` から `全ステイタス対象1次抽選受付` に変わっても、
申し込む先も期限も同じなら、購読者には何のニュースでもないからです。
名前や URL は通知せずに、DB とサイト表示だけ最新化します。

加えて、差分があっても通知しない条件を足しました。

- 過去公演の受付（もう申し込めない）
- 締切を過ぎた受付（同上）
- 期間が全く不明な受付（行動できないし、表記が揺れやすくノイズ源になる）

判断基準はすべて「受け取った人が今から動けるか」です。条件を外れてもデータは更新します。通知に載せないだけです。

結果、通知は毎晩 30〜95 件から 2 件程度になりました。

この経験から得た合言葉が **取り込みは貪欲に、通知はけちに** です。
収集は空振りのコストがほぼゼロなので貪欲でいい。
一方、無駄な通知 1 件は全購読者の時間を奪いますし、一度「当てにならない」と思われたら次から読まれません。

### 購読者全員に誤通知を飛ばした

ひとつやらかしたので書いておきます。

「売り切れ」フラグを差分検知の材料に後から追加したとき、全行のハッシュが一斉に変わりました。
システムから見ればすべての行が「更新された」ように見えるので、購読者全員に一斉に誤通知が飛びました。

いまはハッシュにバージョンの接頭辞を付けて、バージョンが違う行は移行扱いとして通知しないようにしています。

```ts
const HASH_VERSION = "v3";
// → "v3:57f2dd29e10bcf91..."
```

コードには「ハッシュの材料を変更したら必ずこの値を上げること」という警告コメントを置き、
古いバージョンのハッシュを仕込んで通知が飛ばないことを確認するテストも書きました。

差分検知にハッシュを使うなら、材料を変えた瞬間に全件が差分に見えることは最初から織り込んでおくべきでした。

### 欠けている場所を、アプリ自身に答えさせる

最後に、気に入っている仕組みをひとつ。

1 晩で全公演を深く調べるのは無理があります。
検索の予算には上限があるので、1 公演あたり 2〜3 回の検索に収めると、
チケット特設ページの奥まで読み込む余力が残りません。

そこで収集を 2 段階に分けました。

1. 広く浅く。全公演をひととおり収集する
2. 狭く深く。受付期間が埋まらなかった公演を、アーティスト単位で集中調査する

面白いのは 2 段目の対象の決め方です。
アプリに `GET /api/missing` という API を生やして、いま DB のどこが欠けているかをアプリ自身に答えさせています。

```json
{
  "events": [
    {
      "artist": "あいみょん",
      "date": "2027-02-13",
      "missing_lotteries": ["AIM会員優先予約(抽選)", "..."]
    }
  ]
}
```

これを受け取ったスクリプトが、アーティストごとに専用のプロンプトを組み立てて `claude -p` を起動します。
つまり次に何を調べるべきかを人間が管理していません。DB の状態そのものが調査対象のリストです。

そしてこの仕組みは、前述のラチェットとセットでしか成立しません。
もし上書き方式だったら、せっかく埋めた期間が翌晩の浅い収集で消えて、また `/api/missing` に載ります。
永久に同じ公演を調べ続けることになる。良い方向にしか動かないから、穴が減っていく一方になるわけです。

### いま思うこと

LLM を組み込んだシステムで手こずるのは、間違いより揺らぎのほうでした。
同じ入力でも出力が毎回変わる前提で受け取り側を作る、というのがこの半年で一番身についた考え方です。
識別子を LLM に作らせない、状態は一方向にしか変えない、データを貯めることと人に知らせることを分ける。
どれも冪等性を自分で作る話で、LLM の側は保証してくれません。

逆に言えば、受け取る側さえしっかり作れば、収集そのものは Markdown の指示書で済んでしまうというのが正直な感想です。
